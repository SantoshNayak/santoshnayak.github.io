Domain 1 — Agentic Architecture & Orchestration

Exam Weight: 27%

The Core Concept

In Claude's agentic loop, you own the loop. Claude signals what it wants to do next via stop_reason, and your code acts on it. Claude is stateless — it has no memory between API calls. You must append the full conversation history on every call.

The Correct Loop Pattern

while True:
    resp = client.messages.create(
        model="claude-sonnet-4-6",
        tools=tools,
        messages=messages
    )
    if resp.stop_reason == "end_turn":
        break                          # Claude is done — exit
    # stop_reason == "tool_use" — execute tool
    messages.append({"role": "assistant", "content": resp.content})
    results = execute_tools(resp.content)
    messages.append({"role": "user", "content": results})

The 4 stop_reason Values

stop_reasonMeaningWhat to do
"end_turn"Claude finishedBreak the loop
"tool_use"Claude wants a toolExecute, append result, continue
"max_tokens"Response was cut offIncrease max_tokens, retry
"stop_sequence"Hit a custom stop stringHandle per your app logic

The 3 Anti-Patterns

Anti-pattern 1: Checking content[0].type == "text" to detect completion. Claude can return both text AND tool_use in the same response. Checking for text kills the loop before the tool executes.
Anti-pattern 2: Using iteration cap as the primary stop signal. The cap should only be a safety net, never the primary signal. stop_reason is always primary.
Anti-pattern 3: Parsing natural language like "Task completed" in response.text. You're parsing probabilistic text to make a deterministic control flow decision.
Key Insight: A single response object can contain multiple content blocks of different types simultaneously. The only reliable signal is stop_reason on the response object itself — never check individual content block types to control the loop.
Practice Question
Your agentic loop processes customer requests. During testing, you notice the agent occasionally acknowledges a request ("Sure, let me look that up") but never actually calls the tool. The loop exits after the text response. What is the most likely cause?
❌ Option A: Wrong. Tool description quality affects which tool is selected, not whether the loop processes it. The tool was requested — the loop just didn't execute it.
✅ Option B: Correct. Claude returns both a text block ("Sure, let me look that up") AND a tool_use block in the same response. Checking content[0].type == "text" triggers the break before the tool_use is processed. Fix: check stop_reason == "end_turn" instead.
❌ Option C: Wrong. An iteration cap issue would cause the loop to exit after N turns regardless of Claude's state — not specifically after a text response.
❌ Option D: Wrong. Few-shot examples affect Claude's reasoning, not the loop control flow. The tool was already requested — the loop just didn't process it.

Hub-and-Spoke Architecture

The coordinator is the only hub. It decomposes tasks, delegates to subagents, collects results, and aggregates the final output. Agents never talk to each other directly — all communication routes through the coordinator.

The 5 Unbreakable Rules

Rule 1 — All communication through coordinator. If Agent A needs Agent B's output, the coordinator passes it. Direct agent-to-agent communication breaks observability and error handling.

Rule 2 — Subagents have ZERO context inheritance. Each subagent invocation is completely isolated. Pass ALL context explicitly — the document text, prior findings, expected output format.

Rule 3 — Parallel = multiple Task calls in ONE response. The coordinator emits multiple Task tool calls in a single response to trigger parallel execution. One Task per turn = sequential.

Rule 4 — allowedTools must include "Task" to spawn subagents.

Rule 5 — Coordinator decomposes by goal + quality criteria, not step-by-step instructions.

The Narrow Decomposition Bug

Exam Favourite: When a research system returns results only about a subset of the requested topic, ALL subagents may have executed correctly. The bug is in the coordinator's task decomposition — it decided to only cover certain subtopics. The fix is always to improve the coordinator's breakdown, never to fix individual subagents.
Key Insight: When results are narrow or incomplete but all subagents ran correctly → root cause is always the coordinator's decomposition. Fix the coordinator, not the subagents. This is Universal Rule 2: Root cause over symptom patch.
Practice Question
A multi-agent research system is asked to research "AI applications across industries." The coordinator spawns subagents for healthcare, finance, and manufacturing. The final report is comprehensive for those three sectors but misses retail, education, and logistics. All subagents ran successfully. A developer suggests adding 3 more subagents for the missing sectors. What is the correct fix?
❌ Option A: Wrong. Tool descriptions affect routing, not the scope of what the coordinator asks for. The subagents worked perfectly within their assigned scope.
✅ Option B: Correct. The coordinator decided which sectors to cover and made a narrow decision. Adding subagents patches the symptom — the coordinator will still decompose narrowly next time. Fixing the coordinator's decomposition = root cause fix.
❌ Option C: Wrong. This patches the symptom, not the root cause. The coordinator will still decompose narrowly for different queries. Universal Rule 2: root cause over symptom patch.
❌ Option D: Wrong. Results are returning fine — the report is comprehensive for the covered sectors. The problem is what was asked for, not how results flow back.

The Core Problem Hooks Solve

Claude follows prompt instructions ~99% of the time. For style preferences, 1% deviation is fine. For financial operations, compliance, security — 1% deviation is catastrophic. Hooks move critical rules out of Claude's prompt and into your code, making them 100% deterministic.

Two Hook Types

HookWhen it runsUse for
PreToolUseBEFORE tool executesBlock, gate, enforce prerequisites
PostToolUseAFTER tool executes, BEFORE Claude sees resultNormalise, enrich, sanitize results

The Decision Rule

Mental Test: "If Claude deviates from this instruction once, does something bad happen in the real world?" → Yes = Hook (deterministic). No = Prompt is fine (probabilistic).
SituationUse
Financial operations, identity verification, compliance, securityHooks — deterministic, cannot be bypassed
Formatting preferences, tone, style guidelinesPrompts — occasional deviation is acceptable
Exam Trap: The exam will give scenarios where a prompt instruction sounds correct for financial operations. "Add an instruction: always verify identity before processing refund." This is WRONG for financial operations — it's probabilistic. The correct answer is always a PreToolUse hook.
Practice Question
A developer is building a trading system. Two requirements exist: (1) Trades over $50,000 must never execute without compliance sign-off. (2) The trade confirmation API returns amounts in cents — Claude keeps displaying $150 instead of $1.50. Which combination correctly addresses both?
❌ Option A: Wrong. System prompt for the $50k rule is probabilistic — one missed check on a $50k trade has real financial consequences. Must be a hook.
✅ Option B: Correct. PreToolUse blocks trades over $50k deterministically (cannot be bypassed). PostToolUse converts cents to dollars before Claude sees the result — deterministic normalisation, no misinterpretation possible.
❌ Option C: Wrong. System prompt for currency conversion is probabilistic — Claude might still misinterpret. PostToolUse normalises it deterministically before Claude ever sees the raw value.
❌ Option D: Wrong. PostToolUse runs AFTER tool execution. It cannot BLOCK a trade from executing — too late to prevent the $50k trade.

The Pattern

When multiple tools return data in different formats (currencies, units, date formats), Claude has to compare them in its reasoning. Putting conversion logic inside Claude's reasoning is probabilistic — Claude might forget to convert, or convert incorrectly.

The Correct Architecture

# PostToolUse intercepts BEFORE Claude sees the result
# Conversion happens deterministically in YOUR code
async def normalise_to_usd(input_data, tool_use_id, context):
    result = input_data.get("tool_result", {})
    currency = result.get("currency")
    amount = result.get("price")
    if currency == "EUR":
        rate = get_live_rate("EUR", "USD")
        result["price_usd"] = amount * rate
    return {"modified_tool_result": result}

# Wire to ALL supplier tools
options = ClaudeAgentOptions(hooks={
    "PostToolUse": [
        HookMatcher(matcher="us_supplier", hooks=[normalise_to_usd]),
        HookMatcher(matcher="eu_supplier", hooks=[normalise_to_usd]),
        HookMatcher(matcher="jp_supplier", hooks=[normalise_to_usd])
    ]
})
Key Rule: Multiple tools → different formats → PostToolUse normalises ALL → Claude only sees consistent, normalised data → reliable comparison every time.
Multiple tools returnPostToolUse normalises to
USD, EUR, JPYSingle base currency (USD)
Unix timestamps, ISO dates, natural language datesISO 8601 standard
Celsius, FahrenheitSingle unit

Practice Question
A logistics agent compares delivery times from 3 carriers. FedEx returns hours, UPS returns days, DHL returns business days. Claude keeps picking the wrong carrier because it compares raw numbers without considering units. What is the correct fix?
❌ Option A: Wrong. Puts conversion inside Claude's reasoning — probabilistic. Claude might forget to convert or miscalculate "business days" to hours.
✅ Option B: Correct. PostToolUse intercepts after each tool, before Claude sees results. Normalisation happens deterministically in your code. Claude only ever sees hours — never raw days or business days.
❌ Option C: Wrong. PreToolUse runs BEFORE the tool executes — it can't modify results that haven't been returned yet.
❌ Option D: Wrong. Composite tools reduce flexibility (what if you only need one carrier?), increase maintenance burden, and don't fix the root cause architecturally.

The Stale Context Trap

Exam Favourite: A developer analyses a codebase, takes a break overnight, a teammate merges a large PR. The developer runs --resume. Claude reasons from cached context — file locations, function positions — that are now WRONG. Claude makes changes to wrong files. Fix: Start fresh with structured summary of prior findings, explicitly noting which files changed.
Decision Framework: Has anything changed since the last session? No → --resume. Yes → Fresh start + inject summary. Need to try multiple approaches? → fork_session.
Practice Question
A team needs to explore two migration strategies independently — online migration vs offline migration — without one affecting the other's analysis. Additionally, two new microservices were added to the codebase since the initial analysis. What is the correct session strategy?
❌ Option A: Wrong. Sequential means one strategy's analysis contaminates the other. Also ignores stale context for new microservices.
✅ Option B: Correct. Fork twice = two independent branches from same valid baseline. Fresh + inject for new microservices = stale context avoided, prior findings preserved.
❌ Option C: Wrong. --resume for new microservices is wrong — those files didn't exist in the original session. Context would be stale/missing.
❌ Option D: Wrong. Throwing away entire analysis is wasteful. Original findings are still valid for existing files — only new microservices need fresh analysis.

The Core Problem

When an agent crashes mid-task, all in-context work is lost. --resume doesn't work because the session context is gone. /compact can't run on a crashed session.

The Correct Pattern — JSON Manifest

# Agent exports manifest every 5-10 files
manifest = {
    "high_level_goal": "Find auth vulnerabilities",
    "processed_files": [
        {"path": "src/auth/login.py", "status": "complete",
         "findings": [{"type": "sql_injection", "line": 47}]}
    ],
    "remaining_files": ["src/api/endpoints.py"],
    "key_entities": {"vulnerable_functions": ["get_user"]}
}
Recovery Pattern: Coordinator detects crash → loads last JSON manifest → spawns fresh agent with manifest injected at TOP of prompt → new agent continues from last checkpoint. Zero work lost beyond the checkpoint interval.
Why /compact is wrong for recovery: Agent crashed — context is gone, you can't /compact a dead session. Even if you could, /compact loses exact file names, line numbers, specific findings. Recovery needs EXACT structured data, not prose summaries.
Practice Question
A code analysis agent processes 100 files over 4 hours. It crashes at file 78. The coordinator attempts /compact on the crashed session and sends the summary to a new agent. The new agent starts from scratch despite the summary. What are the root causes?
✅ Option A: Correct. Two root causes: (1) /compact produces prose summaries that lose exact structured data needed for precise recovery. (2) Without periodic JSON manifest export, there's no structured checkpoint data to inject into a recovery agent.
❌ Option B: Wrong. --resume on a crashed session = context is gone, nothing to resume from.
❌ Option C: Wrong. max_tokens affects output length — irrelevant to recovery precision.
❌ Option D: Wrong. /compact every 10 files still produces summaries that lose exact data. Wrong tool entirely — JSON manifest export is the correct mechanism.

Domain 2 — Tool Design & MCP Integration

Exam Weight: 18%

The Core Rule

Tool descriptions are not documentation — they are the routing mechanism. When Claude has multiple tools, it decides which to call based almost entirely on the descriptions. A good description needs: input format with examples, explicit boundaries ("Do NOT use for..."), and ordering hints ("Call BEFORE lookup_order").

System Prompt Keyword Conflicts

Subtle Trap: A system prompt saying "Always verify the customer" creates unintended association — Claude starts calling get_customer even when unnecessary because of the word "verify." Review system prompts for keywords that override well-written tool descriptions.

Practice Question
A developer productivity agent has 3 tools: search_docs (MCP), Grep (built-in), and lookup_api (MCP). The agent consistently uses Grep instead of search_docs for semantic concept searches. The developer adds few-shot examples showing correct tool selection. Misrouting drops from 25% to 18% but doesn't disappear. What is the correct fix?
❌ Option A: Wrong. Few-shot examples treat the symptom. Even dropping from 25% to 18% proves it helps but never fully fixes. The description is still weak — root cause unfixed.
✅ Option B: Correct. Strengthens the MCP tool description to highlight unique capability. Explicitly differentiates from Grep. Root cause fix — Claude now has enough information to route correctly.
❌ Option C: Wrong. Removing Grep throws away a useful tool. The fix should be better descriptions, not fewer tools.
❌ Option D: Wrong. System prompt instruction is probabilistic. "Always prefer" can create its own unintended conflicts elsewhere.

The Correct Error Schema

{
    "isError": true,
    "errorCategory": "transient",   # WHY it failed
    "isRetryable": true,             # WHAT TO DO
    "attemptedQuery": query,         # WHAT WAS TRIED
    "partialResults": partial,       # WHAT WAS FOUND
    "message": "Orders API timed out"
}

The 4 Error Categories

CategoryRetryable?Example
transientYesAPI timeout, network blip
validationYesWrong date format, missing field
businessNoCustomer not eligible, limit exceeded
permissionNoAccess denied, insufficient credentials

The Most Critical Distinction

Access failure vs valid empty result: Database down → isError: true. Customer has no orders → isError: false, results: []. Confusing these causes either infinite retry loops (treating empty as error) or telling customers they have no orders when the database was actually down (treating error as empty).
Silent Suppression Anti-Pattern: Catching a timeout and returning {"results": [], "success": true} is the most dangerous pattern. The coordinator thinks the search succeeded and found nothing. In reality, the search never ran. Customer gets told "no orders found" when they actually have 3 orders.
Practice Question
A customer support agent calls lookup_order which times out. The tool catches the timeout and returns {"results": [], "success": true}. The coordinator tells the customer their order doesn't exist. What is the root cause and correct fix?
❌ Option A: Wrong. Retrying on ALL empty results is dangerous — valid empty results would be retried unnecessarily, causing infinite loops for customers who genuinely have no orders.
✅ Option B: Correct. Silent suppression is the root cause. Fix: return structured error so coordinator knows what happened and can retry or escalate intelligently.
❌ Option C: Wrong. Coordinator instructions are probabilistic. The bug is in the tool's error handling code, not the coordinator's prompt.
❌ Option D: Wrong. PreToolUse runs BEFORE the tool executes — can't detect what happens during tool execution.

A team needs GitHub (team), Jira (team), and a personal Notion server. A new developer must be productive immediately on day one. Which configuration is correct?
❌ Option A: Wrong. Personal Notion in .mcp.json means every teammate gets a server they don't need and can't use without the individual's credentials.
✅ Option B: Correct. Team servers in .mcp.json = every developer gets them automatically on clone. Personal server in ~/.claude.json = stays personal.
❌ Option C: Wrong. GitHub and Jira in ~/.claude.json = every new developer has to manually configure them. Not scalable.
❌ Option D: Wrong. Completely reversed — team tools should be shared via VCS, personal tools should not.

The Core Rule

Give an agent 4-5 tools maximum, scoped to its role. When Claude has 18+ tools, selection becomes unreliable — it confuses similar tools and calls wrong ones regardless of description quality.

Fix: Split into Multiple Scoped Agents

# WRONG — one agent, 18 tools → unreliable selection
# CORRECT — 3 scoped agents, 4-5 tools each
customer_agent   = [get_customer, verify_identity, update_prefs]
order_agent      = [lookup_order, process_refund, track_delivery]
comms_agent      = [send_email, send_sms, escalate_to_human]

Separation of Concerns

When an agent MISUSES a tool (e.g., synthesis agent using web_search to find templates instead of summarising) → the fix is NEVER better instructions. Remove the tool from that agent and route to a dedicated subagent. Tool availability = temptation.
ProblemRoot causeCorrect fix
Tool misrouting (wrong tool from correct set)Vague descriptionsRewrite tool descriptions
Tool misuse (tool outside agent's intended scope)Tool shouldn't be availableRemove tool + dedicated subagent

A customer support system has one agent with 22 tools covering customer management, orders, inventory, communications, and compliance. The team notices increasing misrouting errors. A developer suggests improving all 22 tool descriptions. What is the correct fix?
❌ Option A: Wrong. Better descriptions help but don't solve the fundamental problem — 22 tools is too many regardless of description quality. Symptom patch.
✅ Option B: Correct. Fixes root cause — too many tools. Each agent gets 4-5 focused tools. Coordinator handles routing. Simplest correct intervention.
❌ Option C: Wrong. Reducing to 10 is still double optimal. Arbitrary cut also risks removing needed tools.
❌ Option D: Wrong. Over-engineering — building complexity on top of broken architecture. Simplest correct intervention wins.

Token Efficiency Hierarchy

ToolBest forToken cost
EditSurgical modification of existing fileLow — anchor text only
GrepFind content inside filesLow — matching lines only
GlobFind files by path/nameLowest — paths only
ReadLoad entire file into contextHigh — entire file
WriteCreate/overwrite fileHigh — entire file
BashShell operations (fallback)Variable
Edit vs Read+Write: To append a function to a 3,000-line file, Edit uses only the anchor text (last few lines) + new function. Read+Write loads all 3,000 lines into context then rewrites all 3,000. Edit = surgical and efficient. Read+Write = only when full file restructuring is needed.
Grep vs Glob: "Files that contain X" → Grep (searches contents). "Find *.py files" → Glob (searches paths). Combined: Grep("calculate_tax", "**/*.py") = find Python files containing that function.
Practice Question
You need to append a new utility function to the end of a 3,000-line validators.ts file with the least token overhead. Which approach is optimal?
❌ Option A: Wrong. Write overwrites the entire 3,000-line file — maximum token cost and risk of data loss.
✅ Option B: Correct. Edit processes only the anchor (last few lines) + new content. 3,000 lines never loaded. Surgical, token-efficient, safe.
❌ Option C: Wrong. Loads 3,000 lines into context then rewrites all 3,000. Double the token cost for a simple append.
❌ Option D: Wrong. Over-engineered. Bash piping is error-prone and doesn't leverage Claude Code's native Edit capability.

The Problem

Claude frequently calls get_customer and lookup_order in separate sequential turns, even when both are needed upfront. Each turn = one API round trip. 4+ round trips per resolution = slow.

The Fix

Prompt Claude to emit multiple tool_use blocks in one response. This leverages Claude's native ability to request multiple tools simultaneously — both execute in parallel, results return together before the next API call.

# One response, two tool calls — parallel execution
response.content = [
    {"type": "tool_use", "name": "get_customer", "input": {...}},
    {"type": "tool_use", "name": "lookup_order", "input": {...}}
]
# Both execute simultaneously → one round trip instead of two
Don't build composite tools like get_customer_with_orders. This reduces flexibility (what if you only need one?), increases maintenance burden, and doesn't address the sequential calling pattern architecturally.
Practice Question
Production metrics show 4+ API round-trips per resolution. Analysis reveals Claude calls get_customer and lookup_order sequentially even when both are needed upfront. What is the most effective way to reduce round-trips?
❌ Option A: Wrong. Composite tools reduce flexibility and increase maintenance burden — need a new bundled tool for every common combination.
✅ Option B: Correct. Leverages Claude's native ability to emit multiple tool_use blocks in one turn. Minimal architectural change, maximum impact.
❌ Option C: Wrong. Calls tools that weren't requested, wasting resources. Returns data Claude didn't ask for.
❌ Option D: Wrong. max_tokens affects output length, not tool-calling strategy.

The One Flag That Makes or Breaks CI

# WRONG — interactive mode in CI → job hangs forever
claude "Review this PR"

# CORRECT — non-interactive mode
claude -p "Review this PR" --output-format json

Multi-Pass Architecture

Single pass over 14+ files causes attention dilution — Claude misses bugs in later files. Fix: Pass 1 = per-file local analysis. Pass 2 = cross-file integration review with all per-file findings combined.

Independent Review Instance

Same session self-review = reasoning bias. The generator knows why it made decisions and subconsciously justifies them. Independent review instance with zero prior context catches what self-review misses.

Duplicate Comment Prevention

Include prior findings in context: "Report ONLY new issues or issues still present. Do not repeat already-resolved issues."

Practice Question
A CI pipeline has 3 problems: (1) hangs on every run, (2) duplicate comments on every push, (3) developer who wrote code uses same session to review it. Which fixes address all three?
❌ Option A: Wrong. --max-turns limits iterations, doesn't fix hanging (that's -p). Doesn't address duplicate comments.
✅ Option B: Correct. -p fixes hanging. Prior findings fix duplicates. Independent instance fixes self-review bias. All three root causes addressed.
❌ Option C: Wrong. Clearing comments = visual fix, not root cause. Claude still re-analyses resolved issues.
❌ Option D: Wrong. --output-format doesn't fix hanging. Same session still has reasoning bias.

Domain 4 — Prompt Engineering & Structured Output

Exam Weight: 20%

The Core Problem

Vague instructions like "be conservative when flagging issues" produce inconsistent results. Claude interprets "conservative" differently each time. Fix: Explicit categorical criteria with inclusion AND exclusion lists.

The False Positive Trust Cascade

Most tested concept in D4.1: One category with high false positives → developers ignore ALL categories → even accurate findings get dismissed → entire tool becomes useless. Counterintuitive fix: Disable the bad category first → restore trust → fix in isolation → re-enable.
Severity calibration: Never use vague levels like "high = serious issues." Use concrete code examples: high = SQL injection, hardcoded credentials. medium = missing input validation, unhandled exceptions. low = inconsistent error messages.
Practice Question
A CI pipeline reviews PRs for security (95% accurate), deprecated APIs (92% accurate), and code style (55% false positive rate). Developers have stopped reading ALL PR comments. What is the correct immediate fix?
❌ Option A: Wrong. Doesn't address the immediate problem — developers already stopped reading ALL comments. Trust must be restored first.
❌ Option B: Wrong. Partial reduction in false positives won't change developer behaviour — they're already ignoring everything.
✅ Option C: Correct. Disable high-FP category → developers trust accurate categories again → fix style in isolation → re-enable when accurate.
❌ Option D: Wrong. Permanent removal throws away a useful category. Goal is fix, not eliminate.

The Core Rule

Show reasoning, not just answers. Claude generalises the reasoning pattern to novel inputs — not just the specific examples. Few-shot examples without reasoning = Claude memorises cases. With reasoning = Claude learns the decision pattern.

5 Situations and Their Example Types

SituationExample needed
Ambiguous classificationShow reasoning for why one choice wins over alternatives
Output format inconsistentShow exact output shape expected
Too many false positivesShow what TO flag AND what NOT to flag
Different document structures failingShow correct extraction for each format variation
Informal measurements not extractedShow mapping from informal to standard units
How many examples: 2-4 targeted examples on ambiguous cases only. Don't add examples for obvious cases — wastes tokens. The exam won't ask you to name the "type" — just recognise the situation and pick the right fix.
Few-shot is NOT correct for: Tool misrouting (fix descriptions instead), absent data (fix schema), control flow bugs (fix code).
Practice Question
A support ticket classifier keeps misclassifying tickets that mention both a bug AND a feature request. What is the correct fix?
❌ Option A: Wrong. Training data doesn't apply — this is a prompt-based classifier, not a fine-tuned model.
✅ Option B: Correct. Few-shot examples with reasoning for ambiguous scenarios. Show: 'Login broken AND want dark mode' → bug, because broken functionality is more urgent than new features. Claude generalises this priority rule.
❌ Option C: Wrong. Over-engineering — one classifier with good examples handles this.
❌ Option D: Wrong. Not all mixed tickets should be bugs. Some might have a higher-priority feature request. Reasoning-based examples handle nuance better than rigid rules.

The Core Problem

Required fields that don't exist in the source document → Claude invents them. This is silent hallucination — no error, no warning, just fabricated data.

The Fix — Nullable Fields

# Make fields that may be absent nullable + remove from required
"vendor_name": {"type": ["string", "null"]}
"required": ["category", "confidence"]  # vendor_name NOT here

Self-Correction Pattern

{
    "stated_total": 500.00,       # what invoice claims
    "calculated_total": 480.00,  # sum of line items
    "conflict_detected": true     # flags discrepancy → human review
}

"unclear" and "other" Enums

Always include escape hatches: "enum": ["bug", "feature", "docs", "unclear", "other"]. "unclear" = signals genuine ambiguity → route to human. "other" + category_detail = captures edge cases.

tool_use guarantees: ✅ Valid JSON, correct types, required fields, enum values. Cannot guarantee: ❌ Semantic correctness (vendor name actually in document, totals matching).
Practice Question
An invoice pipeline occasionally returns PO numbers like "PO-UNKNOWN" and "N/A" for invoices without them. The schema has po_number as a required string. What is the fix?
❌ Option A: Wrong. Few-shot might reduce hallucination frequency but schema still requires the field — Claude still feels compelled to fill it.
✅ Option B: Correct. Nullable type = Claude can honestly return null. Removed from required = not compelled to fill it. Both changes needed together.
❌ Option C: Wrong. Prompt instruction is probabilistic — Claude might still invent values. Schema-level fix is deterministic.
❌ Option D: Wrong. Adding 'unknown' to enum still forces Claude to put something — just labelled hallucination, not honest null.

A company has 3 workflows: (1) pre-merge code check developers wait for, (2) processing 100,000 invoices overnight, (3) research agent using web search across multiple tool calls. Which API choice is correct?
✅ Option A: Correct. Pre-merge = developer waits → Sync. Overnight invoices = no one waiting, high volume → Batch. Research agent = multi-turn tool loops → Sync (batch can't do tool loops).
❌ Option B: Wrong. Pre-merge check — developer is actively waiting. 24hr batch wait is unacceptable.

Attention Dilution

Single pass over 14+ files → Claude misses bugs, gives contradictory findings. Fix: multi-pass architecture.

Pass 1: Per-file local analysis — one call per file, local issues only. Pass 2: Cross-file integration — all per-file findings combined, looking for data flow issues and API contract violations.

Pydantic Validation + Retry

Retry works for: format errors, arithmetic inconsistencies, type mismatches. Retry CANNOT fix: absent data (use nullable fields), genuinely ambiguous data, wrong schema design.

Interview Pattern

For unfamiliar domains: "Before implementing, ask me ALL clarifying questions upfront about domain constraints, edge cases, and failure modes." Use when multiple valid approaches exist and context determines the best one.

Practice Question
An invoice extraction pipeline retries 3 times then fails when processing invoices from a vendor that doesn't include purchase order numbers. What is the correct fix?
❌ Option A: Wrong. More retries = more attempts at finding data that doesn't exist. Infinite retries won't create information.
❌ Option B: Wrong. Few-shot examples help format understanding — but data is genuinely absent, not misformatted.
✅ Option C: Correct. Absent data = schema design problem, not retry problem. Nullable = honest null. Retry reserved for format/arithmetic errors only.
❌ Option D: Wrong. Interview pattern is for implementation approach, not missing fields in extraction.

The Pattern

High-stakes outputs need a verification pass — a second Claude instance evaluates the first's output before it reaches the user.

Pass 1 = generate. Claude drafts the response. Pass 2 = independent verify. Fresh instance evaluates against policy, accuracy, tone. Outputs confidence + recommendation: send / human_review / regenerate.

Why Independent Instance

Same instance self-review = reasoning bias. Knows why it made decisions → subconsciously justifies → misses its own mistakes. Independent instance with zero prior context reviews purely on merit.

Tiered Routing

VIP customers = higher threshold (0.95) for auto-send. Standard = lower threshold (0.75). Enterprise = always human review regardless of score.

Disclaimer vs verification pass: Disclaimer = reactive (wrong response already sent). Verification pass = proactive (catches issues BEFORE sending). For high-stakes outputs, always verification pass.
Practice Question
An enterprise deploys Claude to categorise tickets and draft responses for VIP clients. They're worried about incorrect responses reaching VIPs. Which design is most appropriate?
❌ Option A: Wrong. Defeats purpose of automation — human handles everything, no AI value.
❌ Option B: Wrong. Reactive, not proactive. Wrong response already sent to VIP. Disclaimer doesn't prevent damage.
❌ Option C: Wrong. Improves style, not accuracy. Doesn't catch factual errors or policy violations.
✅ Option D: Correct. Proactive quality gate. Catches issues BEFORE sending. Routes intelligently based on evaluation.

Domain 5 — Context Management & Reliability

Exam Weight: 15%

Case Facts Block

Critical data placed at the TOP of every prompt, verbatim, never summarised. Survives /compact because it's injected fresh each time, outside conversation history.

prompt = f"""
CASE FACTS (do not summarise):
{json.dumps(case_facts, indent=2)}

[summarised conversation here]

USER: {current_message}
"""

Lost-in-Middle Effect

Claude processes information at start and end most reliably. Information buried in middle of long context is often missed. Fix: critical facts at TOP always.

Tool Output Trimming

40-field API response → trim to 5 relevant fields before passing to Claude. Saves 87% context space.

Scratchpad Files

For extended exploration: agent writes findings to scratchpad.md as it explores. Implementation agent reads scratchpad with clean context. Prevents context degradation.

Practice Question
A customer support agent starts saying "a significant amount" instead of $8,450.00 after 15+ turns. A developer suggests increasing context window size. What is the correct fix?
❌ Option A: Wrong. Larger window delays the problem but doesn't fix lost-in-middle. Values still get buried regardless of window size.
❌ Option B: Wrong. /compact is what's CAUSING values to become vague summaries. More /compact = more data loss.
✅ Option C: Correct. Case facts at TOP = exact values preserved, reliably processed, survives /compact because injected fresh outside conversation history.
❌ Option D: Wrong. Fresh session loses all prior conversation context. Customer must repeat everything.

3 Valid Escalation Triggers

1. Customer explicitly requests human → IMMEDIATE escalation, no offer to resolve first.
2. Policy gap → no clear rule for edge case → escalate, don't guess.
3. Cannot make progress → 3 failed attempts → escalate with full context.

2 Unreliable Triggers (Anti-Patterns)

Sentiment-based escalation: "Customer seems frustrated" → WRONG. Frustrated customers often want resolution, not transfer. Use explicit categorical criteria.
Self-reported confidence scores: "I'm 60% confident" → WRONG. Claude's confidence scores are uncalibrated. Not a reliable signal.
Multiple customer matches: Don't pick by heuristic, don't escalate immediately. Ask for more identifiers (email, order number). Only escalate if customer can't provide them.
Practice Question
A customer says: "I don't care what your policy says, I want to talk to your manager right now." The agent responds: "Let me try one more thing." What's wrong?
❌ Option A: Wrong. Escalation based on frustration detection (sentiment) is unreliable.
✅ Option B: Correct. Explicit human request = immediate escalation. No exceptions. Offering one more resolution attempt after explicit request = disrespectful.
❌ Option C: Wrong. Customer asked for human, not a callback. Immediate escalation, not alternative options.
❌ Option D: Wrong. Confidence scores are uncalibrated — unreliable trigger. Explicit request overrides everything.

Two Anti-Patterns — Both Equally Wrong

Silent suppression: Catching timeout → returning empty success. Coordinator makes wrong decisions on false data.
Full abort: sys.exit(1) on any error. Throws away ALL successful subagent results because one failed.

The Correct Pattern

Structured error propagation with failureType, partialResults, and isRetryable. Coordinator makes intelligent recovery decisions. Gap annotation preserves what succeeded and marks what failed.

Key principle: Preserve what succeeded, annotate what failed, let the coordinator decide recovery strategy based on structured error context.
Practice Question
5 subagents run in parallel. 4 complete successfully. The 5th times out halfway through with 3 articles found. A developer catches the timeout with sys.exit(1). What is the correct fix?
❌ Option A: Wrong. Silent suppression — trades one anti-pattern for another. Loses the 3 partial articles.
✅ Option B: Correct. Structured error preserves partial results. 4 successful results kept. Coordinator annotates gap in final report.
❌ Option C: Wrong. Retry might work for transient errors but doesn't fix sys.exit(1). Also loses 3 articles already found if retried.
❌ Option D: Wrong. Over-escalation. 4 subagents completed. Coordinator can handle this intelligently.

The Core Problem

Claude's raw confidence scores are uncalibrated. Raw 0.98 ≠ 98% accurate. After testing on labeled data, raw 0.98 might only be 84% accurate. This is overconfidence.

Calibration Process

Step 1: Build labeled validation set (correct answers known). Step 2: Run model, record raw confidence + actual accuracy. Step 3: Map raw scores to empirical accuracy (Expected Calibration Error). Step 4: Set routing threshold on CALIBRATED probability, not raw score.

Blocking vs Async Human Review

TypeWhen to useExamples
BlockingIrreversible actions, high cost of errorPayments, account deletion, legal delivery
AsyncReversible actions, lower stakesContent moderation, draft quality, recommendations
Practice Question
A medical diagnosis assistant outputs confidence scores averaging 0.92. The team sets auto-send threshold at 0.85. After deployment, 18% of auto-sent diagnoses contain errors. What went wrong?
❌ Option A: Wrong. Higher threshold on uncalibrated scores is still arbitrary. Raw 0.95 might still only be 80% accurate.
✅ Option B: Correct. Raw 0.92 doesn't mean 92% accurate. Calibration reveals true accuracy. Route on calibrated probability, not misleading raw score.
❌ Option C: Wrong. This is about calibration and routing, not model training.
❌ Option D: Wrong. Defeats purpose of automation. Calibrated routing handles this more efficiently.

The Absolute Rule

When two sources conflict — annotate both with source and date. Never pick one. Never average them. Averaging creates an invented number not supported by either source.

Temporal Differences ≠ Contradictions

Study A (2022): 15% adoption. Study B (2024): 67% adoption. These don't contradict — they show temporal progression. Always check publication dates first.

Genuine Conflicts

Same time period + same metric + different numbers = genuine conflict. Annotate both AND explain methodology difference.

Attribution loss during summarisation: Summaries strip source information. Fix: preserve claim-source mappings separately (like case_facts) — never pass through summarisation.
Practice Question

❌ Option A: Wrong. Recency doesn't mean more accurate. Different methodologies, sample sizes. Discards valid Gartner finding.
❌ Option B: Wrong. Conservative bias is not a selection criterion. Picking either one discards the other.
✅ Option C: Correct. 34% is a fabricated number neither source supports. Annotate both honestly. Reader makes informed judgment.
❌ Option D: Wrong. More sources help context but don't fix the immediate problem of averaging.
