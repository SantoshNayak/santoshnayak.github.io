The 3 Universal Decision Rules

1. Deterministic over probabilistic when stakes are high. Financial / legal / compliance = hooks and prerequisites. Style preferences = prompts are fine.

1.1 — The Agentic Loop

The loop is model-driven: Claude decides which tool to call next based on context. You only drive the scaffolding — check stop_reason, execute the tool, append result to history, repeat. This differs from a hard-coded decision tree where you dictate the sequence.

❌ All 3 anti-patterns
# WRONG 1: text content check
if response.content[0].type == "text":
    break  # Claude returns text AND
           # tool_use in same response

# WRONG 2: iteration cap as primary
for i in range(10): ...

# WRONG 3: natural language
if "Task completed" in text:
    break
✓ Correct pattern
while True:
    resp = client.messages.create(
        model="claude-sonnet-4-6",
        max_tokens=4096,
        tools=tools,
        messages=messages
    )
    if resp.stop_reason == "end_turn":
        break  # PRIMARY signal
    # stop_reason == "tool_use"
    messages.append({"role":"assistant",
                      "content":resp.content})
    results = execute_tools(resp.content)
    messages.append({"role":"user",
                      "content":results})

The subtle trap: Claude returns a text block AND a tool_use block in the SAME response. Checking content[0].type == "text" kills the loop before the tool executes. The agent acknowledges the request and silently does nothing.

From GitHub guide: The full API request structure — model, max_tokens, system, messages, tools, tool_choice. All four stop_reason values matter: "end_turn", "tool_use", "max_tokens" (truncated — increase limit), "stop_sequence" (handle per app logic). You must send the full conversation history on every API call — the model is stateless between requests.

1.5 — Hooks: Deterministic vs Probabilistic

from claude_agent_sdk import ClaudeAgentOptions, HookMatcher

# PreToolUse: BLOCK before execution (deterministic gate)
async def block_large_refunds(input_data, tool_use_id, context):
    amount = input_data.get("tool_input", {}).get("amount", 0)
    if amount > 500:
        return {"hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            "permissionDecisionReason": "Refunds >$500 require manager approval"
        }}
    return {}

# PostToolUse: NORMALIZE before Claude sees result
async def normalize_dates(input_data, tool_use_id, context):
    result = input_data.get("tool_result", {})
    if "created_ts" in result:
        result["created_at"] = datetime.fromtimestamp(result.pop("created_ts")).isoformat()
    return {"modified_tool_result": result}

options = ClaudeAgentOptions(hooks={
    "PreToolUse":  [HookMatcher(matcher="process_refund", hooks=[block_large_refunds])],
    "PostToolUse": [HookMatcher(matcher="get_order", hooks=[normalize_dates])]
})
Use hooks whenUse prompts when
Financial operations, identity verification, compliance rulesFormatting preferences, style guidelines, tone
Single failure = real-world consequencesOccasional deviation is acceptable

2.1 — Tool Descriptions Are the Routing Mechanism

❌ Vague — ~12-30% misrouting
get_customer:
  "Gets customer information"
  
lookup_order:
  "Gets order details"
# Both accept "identifier"
# Model guesses based on query words
✓ Explicit — near-zero misrouting
get_customer: """
  Use to verify identity or get account.
  INPUT: customer_email (user@domain.com)
         OR customer_id (CUST-XXXXX)
  OUTPUT: {customer_id, name, status}
  Do NOT use to find orders.
  Call BEFORE lookup_order when
  no order number is available.
"""

From GitHub guide: System prompt wording can create unintended tool associations. An instruction like "always verify the customer" can cause overuse of get_customer even when unnecessary. Review system prompts for keyword-sensitive instructions that might override well-written tool descriptions. Also: agents may prefer built-in tools (Read, Grep) over MCP tools with similar names — strengthen MCP descriptions to highlight unique capabilities.

tool_choiceBehaviorUse when
"auto"Model chooses: tool OR textDefault — flexible responses
"any"Model MUST call a toolGuaranteed structured output; doc type unknown
{"type":"tool","name":"X"}Model MUST call tool XForce ordering: extract_metadata before enrichment

2.2 — Structured Error Responses

# CORRECT: structured — coordinator can make intelligent recovery decision
{
  "isError": True,
  "errorCategory": "transient",   # transient|validation|business|permission
  "isRetryable": True,
  "attemptedQuery": query,
  "partialResults": partial,
  "message": "Orders API timed out after 30s"
}

# WRONG: generic — coordinator cannot recover intelligently
{"isError": True, "content": "Operation failed"}

# CRITICAL DISTINCTION
# Access failure (DB down) → isError: True, isRetryable: True
# Valid empty result (customer doesn't exist) → isError: False, results: []

Catching a timeout and returning {"results": [], "success": True} is the most common anti-pattern. The coordinator assumes the search succeeded and found nothing — no recovery, no escalation, no gap annotation. Always use isError for genuine failures.

4.1 — Explicit Criteria Over Vague Instructions

❌ Vague
"Be conservative"
"Only flag high-confidence issues"
"Check that comments are accurate"
# Inconsistent results every time
✓ Explicit categorical criteria
"Flag ONLY when:
1. Comment contradicts actual code behavior
2. References non-existent function/variable
3. TODO references a bug already fixed

DO NOT flag:
- Stylistically outdated comments
- Missing comments
- Minor wording inaccuracies"

High false-positive rate in ONE category destroys trust in ALL categories. Developers stop reading entirely. Fix: temporarily disable the high-FP category, restore trust in the accurate categories, then improve the bad one in isolation.

4.2 — Few-Shot Prompting

From GitHub guide — 5 types of few-shot examples (all exam-relevant):
1. Ambiguous scenarios: show reasoning for why one action was chosen over plausible alternatives
2. Output formatting: demonstrate exact output shape (location, issue, severity, suggested_fix)
3. Acceptable vs problematic code: reduce false positives while enabling generalization
4. Varied document structures: inline citations vs bibliography vs narrative tables — show correct extraction for all
5. Informal measurements: "two handfuls of rice" → {"amount": "~100g", "precision": "approximate"}

2–4 targeted examples for the AMBIGUOUS cases (not obvious ones). Include reasoning, not just answer — the model generalizes the reasoning pattern to novel inputs, not just the specific examples.

4.3 — JSON Schemas & Structured Output

# Schema design — all patterns from GitHub guide
{
  "type": "object",
  "properties": {
    "category": {
      "type": "string",
      "enum": ["bug", "feature", "docs", "unclear", "other"]  # "unclear" + "other" critical
    },
    "category_detail": {"type": ["string", "null"]},           # freeform when "other"
    "vendor_name": {"type": ["string", "null"]},              # NULLABLE → no hallucination
    "confidence": {"type": "number", "minimum": 0, "maximum": 1},
    "stated_total": {"type": "number"},
    "calculated_total": {"type": "number"},   # self-correction pattern
    "conflict_detected": {"type": "boolean"}  # flags semantic inconsistency
  },
  "required": ["category", "confidence"]   # vendor_name NOT required → nullable
}

From GitHub guide — self-correction pattern: extract both the stated_total and a calculated_total (sum of line_items). If they differ, set conflict_detected: true. This catches semantic errors that JSON schema enforcement cannot catch. Combine with format normalization rules in the prompt: dates always ISO 8601, currency as number + code, percentages as decimals.

Required fields cause hallucination. If vendor_name is required but not in the document, Claude invents a vendor name. Make optional fields nullable (type: ["string", "null"]) and remove from required. tool_use eliminates syntax errors but NOT semantic errors.

4.6 — Prompt Chaining & Multi-Instance Review (From GitHub Guide)

Prompt chaining: break complex review into focused sequential passes. Each step receives the previous step's output.

# Prompt chaining for code review
Step 1: "Analyze auth.ts for local issues only" → auth_issues
Step 2: "Analyze database.ts for local issues only" → db_issues
Step 3: f"Integration pass. auth_issues={auth_issues}, db_issues={db_issues}.
         Identify cross-module data flow issues."

# Why: avoids attention dilution (model misses bugs when processing 14+ files at once)
# Prompt chaining vs dynamic decomposition:
# Chaining: predictable, repeatable tasks (always same structure)
# Dynamic: open-ended investigation (structure emerges during execution)

Interview pattern (from GitHub guide): before implementing, Claude asks clarifying questions. Use when: unfamiliar domain (fintech, healthcare), tasks with non-obvious implications (cache strategies, failure modes), multiple viable approaches where context determines best choice.

# Pydantic validation-retry (GitHub guide addition)
from pydantic import BaseModel, validator

class InvoiceExtraction(BaseModel):
    total: float
    line_items: list[LineItem]
    
    @validator("total")
    def total_must_match_items(cls, v, values):
        calc = sum(i.amount for i in values.get("line_items",[]))
        if abs(v - calc) > 0.01:
            raise ValueError(ff"Total {v} ≠ sum of items {calc}")
        return v
# On ValidationError → retry with: doc + failed extraction + specific error message
# Retry works: format errors, structural errors, arithmetic inconsistencies
# Retry fails: information absent from source document
